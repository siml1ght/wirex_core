# ТЗ: Разработка игрового прокси-туннеля "Hydra-Tunnel" с защитой от ТСПУ

### Контекст проекта
* **Цель:** Создать легковесный, приватный VPN/прокси-туннель для Windows и Linux.
* **Назначение:** Обеспечение минимального пинга и нулевой потери пакетов (Packet Loss) в онлайн-игры из РФ через зарубежный VPS.
* **Главная угроза:** ТСПУ (DPI с ИИ-анализом поведенческих паттернов трафика: таймингов, размеров пакетов, тикрейта и фиксации постоянных IP:PORT сессий).
* **Язык реализации:** Go (Golang) для кроссплатформенного клиента и сервера.

---

## 1. Архитектурная концепция (Уход от сигнатур)
Система полностью отказывается от концепции единого TLS-туннеля. Вместо этого игровой UDP-трафик, перехваченный с виртуального интерфейса (TUN), динамически расщепляется (Multi-Path) и отправляется на сервер тремя разными путями:
1. **Канал «DNS» (Порт 53 UDP):** Пакеты маскируются под легитимные системные DNS-запросы.
2. **Канал «WebRTC» (Порт 3478 UDP):** Пакеты маскируются под STUN-заголовки (видеозвонки, Discord).
3. **Канал «Hopping» (Динамический диапазон):** Пакеты летят на псевдослучайные порты сервера, меняющиеся каждую секунду по алгоритму TOTP (Time-based One-Time Password).

---

## 2. Интеллектуальные геймерские модификации

### 2.1 Алгоритм «Упреждающего дублирования» (Proactive Replication)
* Чтобы компенсировать разницу в задержках (Jitter) между каналами, мелкие пакеты управления (размером до 200 байт: выстрелы, нажатия клавиш) клиент отправляет одновременно во все доступные каналы сразу с одинаковым Sequence Number.
* Сервер принимает тот пакет, который прилетел первым, а дубликаты, пришедшие позже через медленные каналы, мгновенно отбрасывает. Пинг игры всегда равен пингу самого быстрого канала в данную миллисекунду.

### 2.2 Динамический сетевой оркестратор (Adaptive RTT Weighing)
* Клиент и server непрерывно измеряют RTT и Packet Loss каждого канала. 
* Тяжелые пакеты игры (размером более 500 байт: скины, данные мира) отправляются только в тот канал, который прямо сейчас имеет минимальный пинг. Медленные каналы в этот момент заполняются «шумовыми» пакетами-пустышками (Padding), чтобы ТСПУ продолжал видеть там непрерывную активность стандартного размера и не закрывал сессию.

### 2.3 Метод «Слияния пакетов» (Packet Aggregation) для обмана ИИ
* Внедрение микро-буфера на стороне клиента (задержка не более 1–2 мс). Если за эту микросекунду игра создала несколько мелких UDP-пакетов, они упаковываются в один большой легитимный пакет, размер которого полностью соответствует стандартному пакету передачи потокового видео или загрузки веб-страницы, полностью ломая игровой паттерн тикрейта для ИИ ТСПУ.

## 3. Технические требования к компонентам

### 3.1 Клиент (Hydra-Client — Windows/Linux)
* **TUN-интерфейс:** Создание виртуального сетевого адаптера (использовать библиотеку wireguard-go/tun или netlink).
* **Маршрутизация (Routing):** Перехват трафика только заданных игровых IP-адресов/подсетей (Split Tunneling). Остальной интернет идет напрямую.
* **Модуль мутации (Obfuscation Engine):**
  * Для DNS: Добавление фейкового заголовка транзакции DNS (0x00 0x12), флага запроса и суффикса .com в конец пакета.
  * Для WebRTC: Добавление валидного 20-байтного заголовка STUN Binding Request (первые байты всегда 0x00 0x01).
  * Для Hopping: Вычисление текущего порта сервера по формуле: TargetPort = BasePort + (SHA256(SecretKey + Timestamp_Seconds) % PortRange).
* **Шифрование:** Легковесное AEAD-шифрование (AES-GCM-128 или ChaCha20-Poly1305) только для полезной нагрузки. Заголовки маскировки остаются открытыми для прохождения DPI.

### 3.2 Сервер (Hydra-Server — Linux Ubuntu)
* **Многопоточный Listener:** Постоянный сокет на портах 53 и 3478, а также динамический пул сокетов для Hopping (открытие диапазона портов 40000-50000).
* **Модуль демутации и сборки (Reassembly Engine):** Срезает маскировочные заголовки, расшифровывает полезную нагрузку и восстанавливает исходный порядок пакетов на основе Sequence Number.
* **Проксирование:** Отправка чистого UDP-пакета на целевой игровой сервер и возврат ответа игроку по аналогичной схеме расщепления трафика.

## 4. Спецификация внутреннего заголовка пакета
Каждый пакет, отправляемый внутри маскировочного слоя, должен содержать минимальный оверхед:
```
+-------------------+---------------------+-----------------------+
|  ID сессии (4B)   | Номер пакета (4B)   | Данные игры (Зашифр)  |
+-------------------+---------------------+-----------------------+
```
* **ID сессии (uint32):** Для авторизации пользователей (у каждого клиента свой ID, чтобы сервер различал потоки друзей).
* **Номер пакета (uint32):** Инкрементируемый счетчик для упорядочивания пакетов и фильтрации дубликатов.

## 5. Промпт для ИИ: Написание Шага №1 (Базовый сетевой скелет)

**Инструкция для ИИ-кодера:** Возьми это ТЗ за основу и реализуй первый рабочий прототип по следующему запросу:

```text
Напиши на языке Go прототип клиент-серверного приложения для обхода блокировок игрового UDP-трафика с алгоритмом упреждающего дублирования (Proactive Replication).

Реализуй следующую логику:
1. Клиент принимает массив байт, инкрементирует внутренний счетчик uint32 (Sequence Number) и шифрует данные с помощью ChaCha20-Poly1305.
2. Если размер исходного пакета меньше 200 байт, клиент дублирует его и отправляет ОДНОВРЕМЕННО по двум каналам с одинаковым Sequence Number. Если больше 200 байт — отправляет поочередно (Round-Robin).
3. Первый канал: отправка на порт 53, добавляя в начало пакета фейковый DNS-заголовок (0x44 0x4e 0x53).
4. Второй канал: отправка на порт 3478, добавляя в начало пакета фейковый STUN-заголовок (0x00 0x01).
5. Сервер должен параллельно слушать оба порта (53 и 3478), считывать пакеты, удалять маскировочные заголовки и расшифровывать данные.
6. Сервер должен строго фильтровать дубликаты: если пакет с текущим Sequence Number уже был успешно обработан, его копия, пришедшая позже с другого порта, должна мгновенно уничтожаться (Drop), не вызывая ошибок. Результат выводи в консоль в правильном порядке.

Код должен быть чистым, расширяемым, без использования тяжелых сторонних фреймворков.
```
